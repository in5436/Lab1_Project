# Product Requirements Document (PRD): Server Rack Health Monitor

## A. Загальна ідея
Server Rack Health Monitor- це компактний апаратний модуль для безперервного моніторингу фізичного стану серверного обладнання. Продукт призначений для системних адміністраторів та дата-центрів, де важливо контролювати не лише програмну, а й фізичну безпеку серверів. 

Ця навчальна модель вирішує реальну задачу: фіксує спроби фізичного втручання (удари по корпусу, несанкціоноване відкриття дверцят/бокових панелей) та критичне підвищення температури всередині корпусу. Використання мікроконтролера STM32 дозволяє обробляти дані з трьох різних сенсорів у реальному часі та формувати журнал подій для подальшого аналізу.

## B. Функціональні вимоги
*   **FR-01:** Після запуску система повинна ініціалізувати всі сенсори та вивести в UART повідомлення про успішний старт та поточний стан системи.
*   **FR-02:** Система повинна безперервно (з частотою не менше 10 Гц) зчитувати дані з акселерометра для фіксації ударів чи вібрацій.
*   **FR-03:** Система повинна детектувати відхилення температури від норми (поріг налаштовується програмно) не рідше ніж раз на 1 секунду.
*   **FR-04:** Система повинна миттєво (через зовнішнє переривання EXTI або постійний поллінг) реагувати на розмикання кінцевого вимикача (відкриття дверцят).
*   **FR-05:** При спрацюванні будь-якого з датчиків (удар, перегрів, відкриття), система повинна виводити у UART повідомлення типу "ALARM" із зазначенням причини та timestamp (часу від старту системи).
*   **FR-06:** Система повинна мати два режими: "Охорона" (Active) та "Обслуговування" (Maintenance). У режимі "Обслуговування" тривоги не генеруються, виводиться лише поточна телеметрія.
*   **FR-07:** Для візуальної індикації статусу система повинна використовувати вбудований LED: повільне блимання (раз на секунду)- режим "Обслуговування", швидке блимання- режим "Охорона", постійно увімкнений- зафіксована тривога.
*   **FR-08:** Система повинна мати захист від "дребезгу контактів" (debounce) для кінцевого вимикача, щоб уникнути хибних багаторазових спрацювань (фільтрація сигналів коротших за 50 мс).
*   **FR-09:** Під час виникнення тривожної події система повинна блокувати генерацію нових тривог від цього ж сенсора на 5 секунд (rate-limit), щоб не засмічувати UART-журнал.

## C. Список датчиків

1.  **MPU-6050 (6-DOF IMU)**
    *   **Інтерфейс:** I2C.
    *   **Функціональне призначення:** Фіксує удари по системному блоку, спроби його зсунути або вібрації від несправних кулерів (реалізує вимогу FR-02).
    *   **Альтернативи:** П'єзоелектричний датчик вібрації (SW-420) по GPIO. Відкинуто, оскільки MPU-6050 надає точні кількісні дані прискорення (G) по трьох осях, що дозволяє налаштовувати чутливість програмно, а не "крутилкою" на платі.

2.  **LM35 (Аналоговий термодатчик)** *(у симуляторі емулюється модулем wokwi-potentiometer)*
    *   **Інтерфейс:** ADC.
    *   **Функціональне призначення:** Моніторинг температури всередині серверної стійки. Сигналізує про ризик перегріву (реалізує вимогу FR-03).
    *   **Альтернативи:** Цифрові датчики типу DHT11/DHT22 (1-Wire). Відкинуто, оскільки для виконання вимог лабораторної роботи потрібен сенсор, який використовує класичний АЦП (ADC).

3.  **Кінцевий вимикач (Limit Switch / Tamper Switch)** *(у симуляторі емулюється wokwi-pushbutton)*
    *   **Інтерфейс:** GPIO Input.
    *   **Функціональне призначення:** Детекція несанкціонованого відкриття дверцят стійки або зняття кришки сервера (реалізує вимогу FR-04).
    *   **Альтернативи:** Магнітний геркон. Відкинуто, оскільки механічний кінцевий вимикач є більш стійким до зовнішніх електромагнітних наведень у серверній стійці, хоча принцип підключення до GPIO ідентичний.

## D. План тестування

*   **Тест FR-01 (Ініціалізація):** Запустити симуляцію. Перевірити, що в UART Logger з'явилося повідомлення "System Init OK" і немає кодів помилок HAL.
*   **Тест FR-02 та FR-05 (Реакція на удар):** У режимі "Охорона" змінити значення прискорення по осі X або Y в інтерфейсі Wokwi (імітація удару). Очікується поява повідомлення `[ALARM] SHOCK DETECTED` з поточним часом.
*   **Тест FR-03 (Реакція на перегрів):** Збільшити значення на потенціометрі (емуляторі температури) до максимуму. Очікується повідомлення `[ALARM] HIGH TEMPERATURE` не пізніше ніж через 1 секунду.
*   **Тест FR-04 та FR-08 (Відкриття дверей та Debounce):** "Натиснути" кнопку. Виміряти логічним аналізатором час від зміни стану піна PA1 до появи повідомлення `[ALARM] DOOR OPENED`. Час реакції має бути не менше 50 мс (затримка дебаунсу), при цьому має вивестись лише одне повідомлення, навіть якщо зробити кілька швидких "кліків" мишкою.
*   **Тест FR-06 та FR-07 (Режими та LED):** Перевести систему в режим "Обслуговування". Спровокувати всі три типи тривог. Очікується: відсутність повідомлень `[ALARM]` в UART, LED продовжує блимати з частотою 1 Гц (безперебійна робота основного циклу).
