# Аналіз UART-логів

Усі результати зберігаються у `docs/metrics/lab3/`. Сирі логи S1–S3 лежать без редагування; згенеровані таблиці містяться у `analysis/`.

Для обробки одного сценарію:

```bash
python3 tools/analyze_lab3.py \
  --run S1=docs/metrics/lab3/S1.log \
  --out docs/metrics/lab3/analysis
```

Після запису всіх сценаріїв:

```bash
python3 tools/analyze_lab3.py \
  --run S1=docs/metrics/lab3/S1.log \
  --run S2=docs/metrics/lab3/S2.log \
  --run S3=docs/metrics/lab3/S3.log \
  --out docs/metrics/lab3/analysis
```

### Підтвердження версії прошивки

Прошивка підтримує UART-команду `build`, яка повторно виводить
`[BUILD] git=... clock_hz=... baud=115200` без перезапуску МК.

Скрипти `run_s2.py` і `run_s3.py` надсилають цю команду після
підключення до Wokwi, оскільки початковий банер може бути
пропущений. Для S1 команду `build` потрібно виконати під час
запису журналу.

За наявності `[BUILD]` у всіх нових журналах параметр
`--acknowledge-legacy-build` не потрібен. Відповідність
зібраного ELF перевіряється параметром `--elf`.

Повідомлення `[FIRST_SAMPLE] sensor=... uptime_ms=...`
фіксує перше успішне зчитування датчика. Час відраховується
від запуску системного лічильника HAL, а не безпосередньо
від фізичної подачі живлення.

Для перевірки версії прошивки використовується параметр `--elf`. Якщо UART-лог не містить стартового банера `[BUILD]`, його можна пов'язати з перевіреним ELF лише за явного підтвердження оператора через `--acknowledge-legacy-build`:

```bash
python3 tools/analyze_lab3.py \
  --run S1=docs/metrics/lab3/S1.log \
  --run S2=docs/metrics/lab3/S2.log \
  --run S3=docs/metrics/lab3/S3.log \
  --elf firmware/build/firmware.elf \
  --acknowledge-legacy-build \
  --pair door_open_observed:door_response \
  --out docs/metrics/lab3/analysis
```

Якщо Git-хеш у журналі відрізняється від версії ELF, аналіз зупиняється з помилкою. Параметр підтвердження не дозволяє замінити вже зафіксований інший хеш. Без підтвердження логи з невідомою версією можна аналізувати окремо, але їх не можна вважати доказово сумісними для порівняння.


Для подій із двома часовими мітками МК (`EVT t_us=... name=...`) додайте `--pair початок:кінець`, використовуючи точні назви подій із прошивки. Скрипт розраховує затримку з міток МК, а не з часу отримання рядків хостом. Для звичайного `[ALARM]` без мітки фізичного входу затримка не обчислюється.

| Файл | Дані |
|---|---|
| `analysis/tasks.csv` | Кількість, min/avg/max часу виконання задач |
| `analysis/periods.csv` | Періоди, джитер, пропуски, deadline misses |
| `analysis/system.csv` | Вікно вимірювання, оцінка роботи CPU, RAM, heap, UART, Git-хеш та джерело його підтвердження (`git_origin`) |
| `analysis/bursts.csv` | Передача UART і порівняння з теорією (8N1) |
| `analysis/latencies.csv` | min/avg/max/p99 затримки **лише за парними EVT** |
| `analysis/latency_samples.csv` | Усі виміряні затримки для перевірки |
| `analysis/comparison.csv` | S3 − S1 за однакової встановленої версії прошивки; спосіб її підтвердження наведено в `system.csv` |
| `analysis/summary.txt` | Зведення та попередження |

Якщо в журналі є декілька виводів команди `stats`, для аналізу використовується останній повний набір показників. Це дозволяє уникнути повторного підрахунку накопичених значень.

Показник `work_min_pct` відображає частку часу, витраченого на вимірювані операції. Для окремих затримок додатково може обчислюватися 99-й перцентиль (P99), якщо зібрано достатньо індивідуальних вимірювань.

Для коректного порівняння S1–S3 необхідно використовувати однакову збірку прошивки. Якщо Git-хеш отримано безпосередньо з UART, у `system.csv` зазначається `git_origin=UART`. Для старих журналів без банера допускається явне підтвердження відповідності перевіреному ELF (`git_origin=ELF_OPERATOR_ATTESTED`), яке не є незалежним доказом версії прошивки. Різні зафіксовані Git-хеші вважаються помилкою. Сирі журнали не редагуються. Вимірювання, виконані у Wokwi, розглядаються як результати симуляції.
