# Архітектура FreeRTOS

## 1. Загальна організація

У ЛР4 система Server Rack Health Monitor переноситься з архітектури super loop на FreeRTOS. Основою залишається прошивка ЛР3 для STM32C031C6 з частотою 48 МГц. Підключення датчиків, функціональні вимоги, режими роботи, пороги тривог та формат UART-повідомлень зберігаються.

Для реалізації використовується офіційне ядро FreeRTOS із портом GCC/ARM_CM0 для Cortex-M0+. Основна зміна стосується організації виконання задач. Драйвер MPU6050 та логіка `rack_monitor` використовуються повторно, а функції `Platform_Step()` розподіляються між задачами ОС.

## 2. Задачі та пріоритети

| Задача | Пріоритет | Період або запуск | Призначення |
|---|---:|---|---|
| MonitorTask | 4 | 5 мс | Дверцята, ADC кожні 20 мс, перевірка тривог, LED |
| ImuTask | 3 | 20 мс | Опитування MPU6050 та відновлення після помилок |
| UartRxTask | 2 | Подія UART RX | Приймання та розбір команд |
| UartTxTask | 1 | Черга повідомлень, телеметрія 1000 мс | Передавання UART та обробка відповідей |
| Idle | 0 | Автоматично | Простій процесора та оцінка доступного часу CPU |

Найвищий пріоритет отримує MonitorTask, оскільки вона відповідає за реакцію на відкриття дверцят і формування тривог. Опитування дверцят виконується кожні 5 мс із збереженням debounce 50 мс. Перевірка температури виконується кожні 20 мс. Такий розподіл дозволяє обслуговувати ADC незалежно від стану шини I²C.

ImuTask виконує зчитування прискорення з періодом 20 мс. Якщо датчик недоступний, задача повідомляє про помилку і періодично повторює ініціалізацію. Початковий інтервал повторної спроби становить 500 мс. Інші функції системи при цьому продовжують працювати.

Приймання та передавання UART розділяються, щоб тривала передача не блокувала розбір нових команд. Для виведення використовується одна задача, яка послідовно обслуговує всі повідомлення. Наявні команди та їхні формати залишаються без змін.

## 3. Взаємодія задач

Результат вимірювання MPU6050 передається до MonitorTask через чергу довжиною один елемент. У черзі зберігається останній результат та ознака успішного зчитування. При надходженні нового результату попереднє значення замінюється.

Стан монітора змінюється тільки в MonitorTask. Команди перемикання режимів та очищення тривог передаються їй у вигляді повідомлень. Іншим задачам доступна окрема копія поточного стану для формування відповідей і телеметрії.

Приймання UART працює через переривання та буфер байтів. UartRxTask збирає рядки, перевіряє команди і передає їх на виконання. Повідомлення про тривоги формуються без блокування MonitorTask і передаються до UartTxTask через обмежену чергу. Переповнення буферів і черг фіксується лічильниками.

Доступ до I²C зосереджується в ImuTask. Команди `probe` та `sim_nack` виконуються через неї, тому звичайна робота не потребує одночасного звернення кількох задач до шини.

## 4. Планувальник та пам'ять

Основна конфігурація передбачає витісняльне планування з частотою тіку 1000 Гц. Періодичні задачі використовують `vTaskDelayUntil()`. Передача подій між перериваннями та задачами здійснюється функціями FreeRTOS із суфіксом `FromISR`.

SysTick використовується ядром FreeRTOS. Для мілісекундного лічильника HAL передбачається окремий таймер, а TIM3 з роздільною здатністю 1 мкс зберігається для вимірювань.

Для виділення пам'яті об'єктам ОС планується використання `heap_4`. Розміри стеків та heap спочатку задаються з резервом, а остаточні значення визначаються за фактичним використанням. Контроль переповнення стеків, помилок виділення пам'яті та статистика часу виконання вмикаються для дослідження роботи ОС.

## 5. Порівняння з ЛР3

У ЛР4 зберігаються часові мітки, службові GPIO-маркери PA4, PA6, PA7, вимірювальні команди та сценарії S1, S2, S3. Додатково визначаються завантаження CPU за задачами, запас стеків, використання heap, вартість тіку та перемикання контексту.

Основними критеріями залишаються функціональні вимоги PRD і п'ять гіпотез із `limitations.md`. Поліпшення та погіршення показників оцінюються за фактичними вимірюваннями. Окремо враховуються витрати Flash, RAM і складність синхронізації задач.
