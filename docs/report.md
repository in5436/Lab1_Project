# Звіт з лабораторної роботи №1
**Тема:** Налаштування середовища розробки та bring-up STM32-платформи  
**Виконав:** студент групи ІО-36, Лазінько Р. С.  
**Форма виконання:** В (Wokwi)

## 4.1. Мета лабораторної
Головною метою цієї роботи було закласти надійний технічний та продуктовий фундамент для розробки проєкту Server Rack Health Monitor. На початку завдання здавалося простою інсталяцією програм, проте в процесі стало зрозуміло, що ключова ціль — це ізоляція та відтворюваність. Потрібно було налаштувати конвеєр збірки через Docker і Makefile так, щоб код компілювався без прив'язки до локальної ОС, а мікроконтролер був правильно ініціалізований через STM32CubeMX.

Оскільки робота виконується за формою В, практичним критерієм успіху стало базове налаштування віртуального мікроконтролера та успішний запуск прошивки у симуляторі Wokwi із виведенням логів у UART і тестовим керуванням LED. Також важливою складовою було продуктове планування: аналіз реальних апаратних компонентів та створення PRD із чітким планом тестування на майбутнє.

### Проблеми та їх вирішення

### Проблема №1: Помилка автентифікації під час push-запиту в репозиторій
* **Що відбувалося (симптом):** Консольний клієнт Git відхиляв спробу зробити git push з помилкою автентифікації (Authentication failed), хоча пароль від акаунту був введений правильно.
* **Що виявилось причиною (root cause):** З міркувань безпеки GitHub повністю скасував підтримку звичайних паролів для базової автентифікації через термінал на користь токенів.
* **Як полагодили:** У налаштуваннях розробника на GitHub було згенеровано Personal Access Token (PAT) і використано його замість пароля для авторизації в терміналі. (Локальне налаштування ОС).

### Проблема №2: Блокування конфігурації USART2 у CubeMX
* **Що відбувалося (симптом):** У розділі Connectivity опція USART2 відображалася сірим кольором (була заблокована), через що неможливо було змінити швидкість на 115200 біт/с та налаштувати асинхронний режим.
* **Що виявилось причиною (root cause):** Під час створення проєкту було залишено стандартні галочки ініціалізації периферії плати ("Initialize all peripherals with their default Mode"). Це жорстко прив'язало піни та створило прихований конфлікт альтернативних функцій.
* **Як полагодили:** Проєкт у CubeMX було створено наново без дефолтної ініціалізації. Це дозволило вручну активувати USART2 та призначити його на піни PA2/PA3 ([коміт 79c839b](https://github.com/in5436/Lab1_Project/commit/79c839b)).

### Проблема №3: Відсутність рекомендованої плати у симуляторі Wokwi
* **Що відбувалося (симптом):** Під час налаштування симуляції виявилося, що рекомендовані в методичці плати (F411RE/F446RE) недоступні у каталозі компонентів Wokwi.
* **Що виявилось причиною (root cause):** Поточна версія симулятора Wokwi просто не підтримує мікроконтролери серії STM32F4.
* **Як полагодили:** Проєкт одразу адаптовано під наявну в Wokwi модель board-st-nucleo-c031c6, а в CubeMX згенеровано відповідний код для NUCLEO-C031C6 ([коміт 79c839b](https://github.com/in5436/Lab1_Project/commit/79c839b)).

### Проблема №4: Розсинхронізація та зсув курсора миші у віртуальній машині
* **Що відбувалося (симптом):** Під час налаштування середовища в Ubuntu на віртуальній машині кліки мишкою реєструвалися зовсім не в тому місці, куди вказував курсор на екрані.
* **Що виявилось причиною (root cause):** Типова проблема з драйверами інтеграції миші (Mouse Integration) або конфлікт масштабування дисплея (Display Scaling) між хостовою операційною системою та гостьовою ОС.
* **Як полагодили:** Оскільки графічний інтерфейс реагував неадекватно, для економії часу навігацію в терміналі та редагування файлів було виконано виключно за допомогою клавіатури (стрілочки, клавіша Tab та гарячі клавіші).

### Проблема №5: Кешування старих артефактів під час перекомпіляції коду
* **Що відбувалося (симптом):** Внесені в main.c зміни не відображалися у Wokwi після повторного виклику `make build`. Симулятор продовжував використовувати стару версію прошивки.
* **Що виявилось причиною (root cause):** Початковий Makefile не мав механізму примусового очищення об'єктних файлів, тому система збірки вважала, що перекомпіляція не потрібна, і залишала старий файл firmware.elf.
* **Як полагодили:** Оптимізовано кореневий Makefile: додано ціль `clean` для швидкого очищення директорії firmware/build, а також захист `.PHONY` ([коміт 6d742df](https://github.com/in5436/Lab1_Project/commit/6d742df)).

## 4.4. Висновок
У ході виконання лабораторної роботи було успішно налаштовано ізольоване середовище для розробки під мікроконтролери STM32 за допомогою Docker та Makefile. Практично закріплено навички конфігурації базової периферії (USART, I2C, ADC, GPIO) через STM32CubeMX на прикладі плати NUCLEO-C031C6. Успішний запуск прошивки в симуляторі Wokwi, що підтвердився виводом логів через UART та перемиканням стану LED, довів правильність налаштування всього build-конвеєра. Також було проаналізовано апаратні компоненти та складено PRD для майбутнього проєкту «Server Rack Health Monitor».

У наступній лабораторній роботі (ЛР 2) планується перехід від базового налаштування до написання логіки датчиків: реалізація опитування MPU-6050 через шину I2C та налаштування зчитування значень з фоторезистора через ADC. Зважаючи на отриманий досвід, у майбутньому варто одразу закладати оптимізований Makefile з цілями очищення (clean) та автоматизованою збіркою образу, щоб уникати втрати часу на проблеми з кешуванням під час компіляції.
