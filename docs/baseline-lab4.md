# Базова лінія для ЛР4

Документ фіксує результати ЛР3 для **Server Rack Health Monitor** та порядок їх повторення після переходу на FreeRTOS. Порівнювати потрібно однакові сценарії, часові точки й умови вимірювання. Наведені значення отримано у Wokwi.

## 1. Конфігурація та ідентифікація вимірювань

| Параметр | Значення |
|---|---|
| Плата й архітектура | STM32C031C6, Cortex-M0+, super loop без ОС |
| Симуляція | Wokwi, основна схема `diagram.json` |
| Тактування | 48 МГц |
| Інтерфейс команд і журналу | USART2, 115200 бод, 8N1, RFC2217 `localhost:4000` |
| MPU-6050 | I²C1, PA9/PA10, адреса `0x68`, номінальне опитування 20 мс |
| Температура | ADC1_IN0, PA0, потенціометр `temp1` як модель LM35, опитування 20 мс, поріг 45°C |
| Дверцята | PA1, debounce 50 мс, обмеження повторних тривог 5 с |
| Телеметрія | Період 1000 мс |
| Ідентифікатор прошивки в S1–S3 | `c1d1d3a82c1e` з UART-повідомлення `[BUILD]` |

У журналах S1–S3 зафіксовано однаковий ідентифікатор прошивки `c1d1d3a82c1e`. Контрольну суму зібраного ELF наведено в [`memory-build.txt`](metrics/lab3/memory-build.txt). Для коректного порівняння з ЛР4 необхідно зберегти ідентифікатори збірок та використовувати однакові умови вимірювання.

## 2. Відтворення основних сценаріїв

Команди нижче виконуються з кореня репозиторію. Спочатку зібрати прошивку (`make build`), запустити Wokwi у VS Code та перевірити `[BUILD]`, `[SELF-TEST]` і появу `[TELEMETRY]`. У `wokwi.toml` налаштовано порт 4000. Для повторних прогонів використовувати **нові шляхи**, не перезаписуючи докази ЛР3.

| Сценарій | Умови та порядок виконання | Джерело ЛР3 |
|---|---|---|
| **S1, простій** | `ACTIVE`, 25,1°C, нерухомий MPU-6050, дверцята зачинено. У UART виконати `build`, `stats reset`, почекати приблизно 55 с без подій, потім `stats`, `mem`, `uart stats`. Зберегти повний UART-журнал. У ЛР3 вікно статистики становило 55,280 с. | [`S1.log`](metrics/lab3/S1.log) |
| **S2, номінальний** | Ті самі сенсори, без навмисних тривог; звичайна телеметрія та рідкісні команди. Запустити `python3 tools/run_s2.py --minutes 60 --out docs/metrics/lab3/repeat-S2.log`. Скрипт перемикає `maint` на 15-й хвилині й `active` на 17-й, надсилає `status`, `probe`, `mem` і підсумкові команди. Тривалість основного прогону 60 хв. | [`S2.log`](metrics/lab3/S2.log), [`S2-actions.csv`](metrics/lab3/S2-actions.csv) |
| **S3, максимальний** | Активні всі сенсори. Запустити `python3 tools/run_s3.py --minutes 3 --out docs/metrics/lab3/repeat-S3.log`. Скрипт надсилає `load 4096` кожні 5 с, періодично `status`, `probe` і серії команд. Окремо під час прогону створювати у Wokwi удар, перегрів і відкриття дверцят. Ці впливи скрипт **не генерує**; їхні моменти треба фіксувати окремо. | [`S3.log`](metrics/lab3/S3.log), [`S3-actions.csv`](metrics/lab3/S3-actions.csv) |

Час виконання сценаріїв скрипти відраховують за часовими мітками `ts` у телеметрії мікроконтролера. У S3 UART-навантаження створюється автоматично, а тривожні події відтворюються вручну в Wokwi. У збереженому `S3.log` зафіксовано 21 повідомлення `[ALARM]`. Для підсумкового аналізу використовується останній повний блок `[STATS]`.

Перевірка зникнення живлення під час запису у Flash не проводилася, оскільки в поточній реалізації журнал подій передається через UART і не зберігається у Flash.

## 6. Вимірювальний інструментарій для ЛР4

- **Час МК:** TIM3 із кроком 1 мкс (`firmware/Platform/perf.c`), `HAL_GetTick()` для розкладу задач; DWT для Cortex-M0+ у цій прошивці не використовується.
- **UART-журнал:** `[BUILD]`, `[TASK]`, `[PERIOD]`, `[STATS]`, `[LOAD]`, `[MEM]`, `[BURST]`, `[UART_RX]`, `EVT t_us=... name=...`. Мітки часу брати з МК, не з часу приходу рядка на хост.
- **Команди:** `build`, `stats reset`, `stats`, `mem`, `uart stats`, `uart reset`, `load 256` ... `load 4096`, `status`, `probe`, `maint`, `active`. Для ЛР4 зберегти назви та зміст метрик і точок вимірювання.
- **Логічний аналізатор Wokwi:** D0 = PA9/I²C SCL, D1 = PA10/I²C SDA, D2 = PA2/UART TX, D3 = PA1/дверцята, D4 = PA4/ADC, D5 = PA3/UART RX, D6 = PA6/IMU, D7 = PA7/маркер реакції на дверцята. Буфер у схемі: 10 000 000 переходів; у PulseView для великих VCD використовувався `Downsampling factor = 100/200`.
- **Звіт пам’яті:** `tools/memory_report.sh` використовує `arm-none-eabi-size`, `nm`, `.map` і статичні кадри стека з `.su`. Скрипт перезаписує стандартні вихідні файли, тому перед повторним запуском їх треба зберегти.
- **Аналіз на хості:** `tools/analyze_lab3.py`, результати у `docs/metrics/lab3/analysis/`. Для порівняння одного й того самого показника залишити незмінними період, початкову й кінцеву подію, правила підрахунку джитера, пропусків і дедлайнів.

Повторна обробка вже зібраних журналів без перезапису поточних таблиць:

```bash
python3 tools/analyze_lab3.py \
  --run S1=docs/metrics/lab3/S1.log \
  --run S2=docs/metrics/lab3/S2.log \
  --run S3=docs/metrics/lab3/S3.log \
  --pair door_open_observed:door_response \
  --out docs/metrics/lab3/analysis-repeat
```

При порівнянні міток `EVT` і VCD слід вказувати, що початкова точка може відрізнятися: `door_open_observed` фіксується під час програмного опитування, а PA1 у VCD показує фізичний фронт. Висновок про зміну затримки не можна робити за різними визначеннями інтервалу.

## 7. Гіпотези та критерії порівняння з ЛР4

| Обмеження з [`limitations.md`](limitations.md) | Гіпотеза для FreeRTOS | Що порівняти |
|---|---|---|
| 1. Періодичність сенсорів | У S3 максимальний інтервал IMU ≤ 100 мс, пропуски запусків = 0 | Максимум періоду, джитер, `missed` |
| 2. Реакція дверцят | За збереження debounce 50 мс максимум PA1 → PA7 без cooldown ≤ 70 мс | Максимум і розподіл затримок, однаковий набір подій |
| 3. Потік UART-команд | У `flood_during_load` щонайменше 95/100 відповідей | Відповіді, лічильники RX, умови потоку |
| 4. Відмова I²C | За того самого утримання SDA пропуски ADC = 0 | `missed` ADC, час блокування, індикація відмови |
| 5. Неготовий MPU-6050 на старті | Після відновлення доступності перше коректне вимірювання ≤ 1 с без перезапуску | Час до вимірювання та збереження роботи інших каналів |

Крім поліпшень, у ЛР4 потрібно порівняти витрати Flash і RAM, глибину стеків задач, час до першого коректного вимірювання, накладні витрати планувальника та складність налагодження. Окрім можливих покращень зафіксувати також і погіршення.
